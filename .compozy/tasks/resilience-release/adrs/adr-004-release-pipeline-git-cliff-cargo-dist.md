# ADR-004: Hand-assembled PR-gated release workflow using `git-cliff` + `cargo-dist`, no third release-automation tool

## Status

Accepted

## Date

2026-08-19

## Context

The issue scope names two specific tools literally: "release pipeline:
`release.yml` using `cargo-dist`, changelog via `git-cliff`." The operator
confirmed (grill Q5) a PR-triggered flow with a human merge gate before
publishing, "then later see how to automate" — i.e., manual-merge gate now,
revisit automation as a future issue, not this delivery. Market research
found `release-plz` as the common tool implementing exactly this
PR-gated pattern, but `release-plz` has its own built-in changelog
generation and is not `git-cliff` — pulling it in would substitute an
unrequested third tool for the two the issue explicitly named.

## Decision

Assemble the PR-gate pattern from the two named tools plus one small,
undecorated glue action, rather than adopting `release-plz`:

1. A `release-plan` job (on every push to `main`) runs `git-cliff --bump`
   to compute the next version and the changelog diff, then uses
   `peter-evans/create-pull-request` to open/update a single standing PR
   (`release: vX.Y.Z`) with the version bump (`Cargo.toml` workspace
   version) and the `CHANGELOG.md` diff as the PR body and commit.
2. Merging that PR (human gate) creates the version tag — via a
   repo-scoped PAT stored as a secret (not the default `GITHUB_TOKEN`,
   which does not trigger tag-push workflows per the research finding).
3. The tag push triggers `release.yml`, generated by `cargo dist init`
   (`dist-workspace.toml`, not legacy `Cargo.toml` metadata — current
   cargo-dist 0.32.x default), which builds and publishes checksummed
   binaries and pulls release notes from the matching `CHANGELOG.md`
   heading.

## Alternatives Considered

### Alternative 1: Adopt `release-plz` wholesale

- **Description**: Use `release-plz`'s own PR-gate + changelog + tag flow
  end to end.
- **Pros**: Battle-tested, less glue code to maintain.
- **Cons**: `release-plz`'s changelog generation is its own engine, not
  `git-cliff` — using it either drops the issue's literal "changelog via
  git-cliff" requirement or requires fighting `release-plz` to defer to an
  external `git-cliff` run, which is not its designed integration point.
- **Why rejected**: Executable requirements are preserved byte-for-byte
  per this project's operating principle — the issue named `git-cliff`
  specifically, not "a changelog tool." Introducing `release-plz` as an
  undiscussed third dependency is also a speculative-dependency addition
  the operator did not ask for.

### Alternative 2: Tag-triggered only, no PR gate

- **Description**: Skip the standing release PR; a maintainer runs
  `git tag vX.Y.Z && git push --tags` by hand, `release.yml` does the
  rest.
- **Pros**: Simplest possible glue — no `release-plan` job needed.
- **Cons**: No review step before a version number and changelog are
  committed to; contradicts the operator's explicit choice of a human
  gate (grill Q5).
- **Why rejected**: Directly contradicts a confirmed grill decision.

## Consequences

### Positive

- Every tool named in the issue is used for exactly what it was named
  for; no unrequested dependency added.
- The release PR is a real, reviewable diff (version + changelog) before
  anything is tagged or published — matches the confirmed human-gate
  decision.

### Negative

- More glue to write and maintain than adopting `release-plz` wholesale
  (a `release-plan` job plus PAT setup, vs. one Action reference).

### Risks

- The PAT-vs-`GITHUB_TOKEN` requirement is an operator-side setup step
  (creating and storing the secret) — not something this delivery's code
  can automate away; call it out explicitly in the release-plan job's
  Assumptions and in the PR's own review notes.
- Future automation of the merge gate (deferred per Non-Goals) would mean
  swapping the human-merge step for an auto-merge policy — the
  `release-plan` job design should not make that swap structurally hard,
  but building for it now is out of scope.

## Implementation Notes

- `dist-workspace.toml` lists only the `batuta` crate's `[[bin]]` as a
  distributable; `batuta-tui` and `compozy-client` get `publish = false`
  in their own `Cargo.toml` (they are internal libraries, not something
  `cargo-dist`/crates.io should ever try to publish independently).
- `cliff.toml`: `conventional_commits = true`, `filter_unconventional =
  true` (Business Rule, Part I).
- Initial `CHANGELOG.md` is generated once retroactively (`git-cliff
  --tag v0.1.0-beta.1 --unreleased=false` equivalent, full history) as
  part of this delivery's own implementation, not deferred to the first
  automated run.
